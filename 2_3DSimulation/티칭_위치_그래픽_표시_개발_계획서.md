# 시뮬레이션 티칭 위치 그래픽 표시 개발 계획서

- 대상: InoRobot Assistant `2_3DSimulation`
- 작성일: 2026-10-23
- 상태: 기본 티칭 표시와 OLP 지원 구현, 사용성 확장은 후속 범위
- 목표: 저장한 티칭 위치를 로봇을 움직이지 않고 3D 화면에서 확인하고, 화면의 포인트와 프로그램 목록을 서로 선택할 수 있게 한다.

## 1 개발 방향

티칭한 위치마다 **포인트 마커와 번호**를 표시하고, 선택한 포인트에는 **이름, 좌표, 자세축**을 보여준다. 사용자는 위치의 분포와 순서를 확인하고, 목록에서 찾기 어려운 포인트를 그래픽 화면에서 바로 선택할 수 있다.

우선 화면에서 등록한 동작 프로그램의 포인트를 구현하고, 같은 표시 기능에 OLP 프로젝트의 포인트 파일을 연결한다. 기존의 `TCP 경로 선`은 실행하면서 지나간 위치를 보여주므로 독립적으로 유지한다. 저장한 티칭 위치는 프로그램을 실행하기 전부터 표시한다.

대표 완료 시나리오:

> 포인트 3개 티칭 → 티칭 위치 표시 켜기 → 3D 화면에서 P[0], P[1], P[2] 확인 → P[1] 클릭 → 목록의 해당 행 선택 → 현재 위치로 덮어쓰기 → 마커 위치 갱신 → 작업공간 저장과 복구 후 다시 표시

## 2 현재 구성과 재사용 지점

아래는 작성일의 작업공간 소스에서 확인한 구성이다. 구현 시작 시 기존 미커밋 변경과 실제 화면 동작을 다시 확인한다.

| 현재 구성 | 확인한 내용 | 개발에 활용할 부분 |
|---|---|---|
| `main.js`의 `captureRobotMotionStep()` | 포인트 ID, 번호, 이름, 관절값, TCP 위치와 자세, 외부 축을 저장 | 티칭 마커의 원본 데이터 |
| `captureMotionPointCoordinates()`, `motionStepTargetPose()` | 선택한 작업좌표계의 티칭값 저장과 BASE 좌표 변환 | 화면 마커의 좌표 변환 기준 |
| `renderMotionProgramPanel()`, `focusProgramStepRow()` | 동작 목록 표시와 행 접근 | 목록과 마커 선택 연동 |
| `olp-project-core.mjs`의 `parsePointsFile()`, `resolveOlpPoint()` | P, LP, JP 레코드와 파일 경로, 번호, 이름 해석 | OLP 표시 대상 수집과 식별 |
| `renderOlpPointTable()`, `writeOlpPointFromCurrentRobot()` | 포인트 표 표시와 현재 로봇 위치로 수정 | OLP 표 선택 및 수정 후 화면 갱신 |
| `ensureTcpPathOverlayGroup()` 등 TCP 경로 함수 | 별도 장면 그룹, 표시 전환, 자원 해제 | 그래픽 표시 수명 관리 방식 참고 |
| `serializeWorkspaceSnapshot()` 및 복구 경로 | 로봇별 프로그램, TCP, 작업좌표계 등 저장 | 표시 설정 저장과 복구 후 마커 재생성 |
| `requestRender()` | 필요한 시점에 화면 갱신 요청 | 정지 상태에서도 티칭 변경 즉시 반영 |

`buildOlpCartesianTarget()`에는 SCARA 목표값을 동작 범위에 맞추는 보정이 포함되어 있다. 표시 기능에서 이를 그대로 사용하면 원본 티칭 좌표와 다른 곳에 마커가 생길 수 있다. 좌표계 변환 규칙은 공유하되 **원본 좌표를 보정하지 않는 표시 경로**를 마련한다.

## 3 화면과 조작

### 3.1 표시 설정

동작 프로그램 패널의 기존 표시 도구 근처에 `티칭 위치 표시` 버튼을 둔다. 초기값은 꺼짐으로 제안한다. 켜면 현재 선택한 로봇의 동작 포인트를 표시하고, OLP 화면에서는 선택한 포인트 파일을 표시 대상으로 삼는다. 화면에 현재 표시 출처를 명시하여 두 데이터가 혼동되지 않게 한다.

| 표시 요소 | 기본 동작 |
|---|---|
| 포인트 마커 | 티칭한 TCP 위치에 작은 원 또는 십자 표시 |
| 번호와 이름 | 기본은 번호, 선택하거나 가리키면 사용자 이름까지 표시 |
| 선택 강조 | 선택한 점의 테두리와 크기 변경으로 구분 |
| 자세축 | 선택한 점에만 X, Y, Z 방향 표시 |
| 상세 정보 | 원본 좌표, 자세, 로봇 이름, 포인트 출처, 해석에 사용한 작업좌표계 표시 |
| 화면 맞춤 | 선택한 포인트 또는 표시 중인 전체 포인트가 보이도록 카메라 조정 |

확대와 축소에 따라 마커가 지나치게 크거나 작아지지 않게 화면상 크기를 유지한다. 기본은 모델의 앞뒤 관계를 유지하고, 가려진 포인트 확인이 필요하면 `가려진 위치도 표시` 옵션을 제공한다. 화면 밖이나 카메라 뒤의 점은 라벨을 숨긴다.

### 3.2 선택과 기존 기능 연결

1. 목록에서 포인트를 선택하면 해당 마커를 강조한다.
2. 마커를 클릭하면 동작 목록 또는 OLP 표의 해당 행을 선택하고 보이는 위치로 스크롤한다.
3. 같은 위치에 여러 포인트가 있으면 번호와 출처를 고르는 작은 목록을 보여준다. 한 점만 선택 가능한 상태로 방치하지 않는다.
4. 이동은 기존 `해당 위치로 이동` 명령으로 실행한다. 마커의 클릭, 더블클릭, 카메라 맞춤으로 이동 명령을 실행하지 않는다.
5. 포인트 덮어쓰기와 삭제는 기존 편집 기능을 이용하고, 결과를 마커에 반영한다.

마커를 끌어서 티칭값을 변경하는 기능은 후속 범위로 둔다. 카메라 회전·이동, 모델 선택, 측정, 스케치, TCP 스냅과 입력이 겹치지 않게 한다. 드래그를 클릭으로 오인하지 않고, 측정·스케치 등 전용 입력 모드에서는 기존 모드의 입력을 우선한다.

## 4 단계별 범위

| 단계 | 구현 내용 | 완료 기준 |
|---|---|---|
| 1 동작 프로그램 표시 | 현재 로봇의 MOVJ, MOVL 등 위치를 가진 동작에 마커·번호·선택 자세축 표시, 목록 선택 연동, 추가·수정·삭제 반영 | 프로그램 실행 전에도 저장된 모든 유효 티칭 위치를 확인하고 선택할 수 있음 |
| 2 OLP와 복구 | 선택한 파일의 P·LP 표시, JP 변환 지원, 출처 구분, 표시 설정 저장·복구 | 동일 번호가 있는 파일을 바꿔도 정확한 레코드를 표시하고 복구 후 중복 마커가 없음 |
| 3 사용성 확장 | 여러 로봇 동시 표시, 이름 검색, 라벨 밀집 완화, 티칭 순서 연결선 | 포인트가 많아도 필요한 위치를 찾고 구분할 수 있음 |

1단계는 DELAY, WAIT, I/O, VIEW 등 위치 이동이 아닌 명령을 표시 대상에서 제외한다. HOME은 일반 티칭 포인트와 구분하여 초기 범위에서 제외한다. 대상 여부는 기존 `isMotionPointMotion()` 규칙과 실제 실행 의미를 함께 확인한다.

순서 연결선은 3단계에서 선택 기능으로 제공하고 `티칭 순서`라고 표시한다. 단순 연결선을 MOVJ의 실제 이동 궤적이나 충돌이 없는 경로로 설명하지 않는다. OLP 포인트 파일의 나열 순서도 프로그램 실행 순서로 간주하지 않는다.

실제 컨트롤러에서 포인트를 새로 읽어오는 통신 기능, 포인트 자동 생성, 이동 경로 재계산, 충돌 예측은 이번 개발 범위에서 제외한다.

## 5 좌표와 데이터 처리

### 5.1 좌표 변환 원칙

티칭 데이터는 원본값을 유지하고 표시할 때 World 좌표로 변환한다. mm와 deg, 장면의 Z-up 규칙을 유지한다.

- 동작 프로그램: 저장한 `step.tcp`를 기존 `motionStepTargetPose()`와 동일한 의미로 해석한 뒤, 컨트롤러 BASE 프레임을 통해 World 위치와 자세를 계산한다.
- OLP의 P·LP: XYZ와 Rz, Ry, Rx 순서를 지키고, 적용 작업좌표계를 거쳐 World 좌표로 변환한다.
- OLP의 JP: 관절값을 순기구학으로 계산하여 지정한 TCP의 World 위치와 자세를 구한다. 화면에서 움직이는 로봇의 관절값을 임시 변경하는 방식은 사용하지 않는다. 부작용 없는 계산 경로가 없으면 2단계에서 이를 먼저 마련한다.
- 외부 축: 포인트별 외부 축 값에 따른 BASE·작업좌표계 변환을 실행 경로와 맞춘다. 표시용 계산 때문에 현재 로봇이나 설비를 움직이지 않는다.

현재 확인한 동작 포인트에는 포인트별 작업좌표계 ID가 별도로 저장되지 않는다. 1단계는 기존 실행과 동일하게 현재 선택된 작업좌표계로 해석하고, 사용 중인 좌표계를 화면에 표시한다. 작업좌표계를 바꾸면 마커를 다시 계산한다. 포인트별 좌표계 고정 저장은 별도 데이터 형식 변경이므로 이번 단계에 섞지 않는다.

OLP도 파일의 좌표만으로 프로그램의 Tool·Wobj 실행 문맥을 확정하지 않는다. 2단계의 파일 보기에서는 현재 선택한 Tool·Wobj를 표시 기준으로 명시한다. 같은 포인트가 프로그램에서 서로 다른 문맥으로 사용되는 경우의 실행 목표 표시는 후속 범위로 둔다. 동적 Offset과 실행 중 변수 계산 결과도 정적 파일 보기와 구분한다.

### 5.2 데이터 식별과 오류 처리

동작 포인트는 `로봇 ID + step.id`, OLP 포인트는 `로봇 ID + 프로젝트 내 파일 경로 + 원본 심볼 + 번호`로 식별한다. 번호나 이름만으로 연결하지 않는다. 프로그램의 실행 명령과 파일 레코드의 관계도 일대일이라고 가정하지 않는다.

좌표 누락, NaN, 지원하지 않는 축 조합은 원점으로 대체하지 않는다. 해당 마커를 제외하고 표시하지 못한 개수와 이유를 안내한다. 좌표가 유효하지만 로봇이 도달할 수 없는 점은 원래 위치에 표시한다. 도달 가능성이나 충돌을 검사하지 않은 점에 정상·안전 판정을 붙이지 않는다.

TCP 설정 변경 후에도 Cartesian 포인트의 저장된 TCP 목표 좌표는 유지한다. JP는 해당 TCP를 사용한 순기구학 결과가 달라질 수 있으므로 다시 계산한다. 로봇 재배치, 외부 축, 작업좌표계 변경도 필요한 마커만 갱신한다.

## 6 구현 구조와 갱신

새 기능은 데이터 계산과 Three.js 표시를 나누는 두 모듈을 제안한다. 이름은 구현 시 기존 파일 규칙에 맞춰 확정한다.

| 파일 | 역할 |
|---|---|
| `teaching-point-core.mjs` 신규 | 표시 대상 수집, 식별키, 입력 검증, 표시 상태 계산 |
| `teaching-point-scene.mjs` 신규 | 마커·라벨·자세축 생성, 선택 판정, 갱신, 자원 해제 |
| `main.js` | 기존 티칭·OLP·선택·좌표 변환·저장 경로와 연결 |
| `index.html`, `style.css` | 표시 버튼, 상세 정보, 중첩 포인트 선택 UI |
| 언어 자료 | 신규 UI 문구의 다국어 처리 |

마커는 별도 장면 그룹으로 관리하며 충돌 검사, CAD 부품 트리, 모델 내보내기, TCP 스냅 대상에 등록하지 않는다. 프로그램 내보내기에는 그래픽 표시 정보를 추가하지 않는다.

갱신 시점은 티칭 추가·덮어쓰기·삭제, 되돌리기·다시 실행, 프로그램 가져오기, OLP 재해석·파일 전환, 로봇 전환·삭제, 좌표계·TCP·외부 축 변경, 작업공간 복구로 정의한다. 선택만 바뀌면 강조만 갱신하고 전체 마커를 재생성하지 않는다. 실행 중 목표 강조는 실행 상태를 구독하고 선택 강조와 구분한다.

카메라가 움직일 때는 라벨 위치와 마커 크기를 갱신한다. 데이터 변환과 JP 순기구학은 입력이 바뀔 때만 수행하고, 매 프레임 전체 포인트를 계산하지 않는다. 삭제와 복구 시 geometry, material, 라벨, 이벤트 연결을 정리한다.

저장 대상은 표시 켜짐, 이름 표시, 가려진 점 표시 등 사용자 설정으로 한정한다. World 좌표와 그래픽 객체는 저장하지 않고 복구한 원본 데이터로 재생성한다. 구버전 작업공간에 설정이 없어도 기본값으로 열려야 한다.

## 7 검증과 완료 조건

구현 전 현재 티칭 등록, 덮어쓰기, 목록 선택, OLP 파일 전환, 저장·복구를 실제로 확인한다. 아래 시나리오를 계산 테스트와 브라우저 검사로 나누고, 발견한 회귀는 실패하는 재현 테스트부터 추가한다.

| 검증 항목 | 통과 조건 |
|---|---|
| 기본 위치 | 서로 다른 3개 이상의 티칭값이 예상 World 좌표에 표시됨 |
| 좌표계 | BASE, 이동·회전한 Wobj, 재배치한 로봇에서 기존 실행 목표와 좌표 해석이 일치함 |
| 외부 축 | 서로 다른 외부 축 값의 포인트가 현재 축 상태에 끌려가지 않고 해당 목표 위치에 표시됨 |
| TCP와 자세 | TCP 오프셋, 6축 자세, SCARA 회전에서 위치·축 방향이 맞고 원본값을 보정하지 않음 |
| JP | 표시 전후 실제 로봇 관절값과 화면 자세가 같고, 계산된 마커만 갱신됨 |
| 선택 | 목록과 마커 선택이 양방향으로 연결되고 같은 위치의 포인트도 각각 선택 가능함 |
| 데이터 변경 | 추가·수정·삭제·되돌리기 후 이전 마커와 선택이 남지 않음 |
| OLP 식별 | 다른 파일의 같은 번호, P와 LP의 같은 번호, 로봇별 같은 번호를 구분함 |
| 비정상 데이터 | 잘못된 값을 원점에 표시하지 않고, 미표시 이유를 안내함 |
| 기존 조작 | 카메라 회전·이동·확대, 모델 선택, 측정·스케치·스냅이 기존대로 동작함 |
| 실행과 연결 | 표시·선택만으로 로봇이 이동하거나 컨트롤러 명령이 발생하지 않음 |
| 저장과 수명 | 복구 후 표시가 같고, 반복 전환·로봇 삭제 후 마커와 자원이 누적되지 않음 |

좌표 자동 검사의 초기 허용오차는 위치 0.01 mm, 회전 0.01°로 제안하며 기존 계산 정밀도에 맞춰 확정한다. 화면 픽셀 위치만 비교하지 않고 기대 좌표와 변환 결과를 수치로 검사한다.

성능은 같은 PC와 같은 장면에서 기능을 끈 상태와 비교한다. 초기 목표는 1,000개 포인트 표시 시 카메라 조작의 중앙 프레임 시간이 20% 이상 늘지 않는 것으로 제안한다. 라벨은 선택·가리킴 우선으로 제한하고 100개·1,000개·5,000개에서 각각 측정한다. JP 계산은 캐시와 나눠 처리를 적용하여 입력을 막지 않게 한다.

앱 코드·데이터·UI를 변경한 뒤에는 다음 수정에 앞서 `npm run test:fast`를 실행한다. 코드 작업 완료 시 `npm run verify:full`을 실행하고 관련 브라우저 검사를 포함한다. 관계없는 검사 실패도 원인과 미검증 범위를 기록한다. 푸시 요청을 처리할 때는 저장소 규칙대로 검사를 다시 실행하지 않는다.

## 8 작업 순서와 예상 공수

1. 현재 동작과 좌표 변환을 확인하고, 배치·Wobj·TCP·외부 축 기준 사례를 만든다.
2. 1단계의 마커 표시와 선택을 구현하고, 변경·삭제·모드 전환을 검증한다.
3. OLP P·LP와 JP를 연결하고, 표시 문맥과 파일 식별을 검증한다.
4. 저장·복구, 다국어, 자원 해제와 성능을 확인한 뒤 전체 검증을 마친다.
5. 1·2단계 결과를 사용해 본 뒤 다중 로봇과 순서 연결선 등 3단계를 진행한다.

초기 추정은 1·2단계와 검증을 합쳐 **개발자 1명 기준 5~8작업일**이다. 표시 전용 외부 축 변환과 JP 순기구학을 기존 코드에서 분리하는 난이도에 따라 조정한다. 3단계는 별도 추정한다.

버전 기록에는 최종 제공 범위에 맞춰 `티칭한 위치를 3D 화면에서 확인하고 선택할 수 있는 기능을 추가했습니다.`처럼 사용자에게 보이는 결과를 기록한다. 버전 기록 갱신 시 `node tools/build-version-history.cjs`로 홈페이지와 다국어 데이터를 함께 생성한다.

## 9 구현 결과와 확인된 제한

2026-10-23에 동작 프로그램의 MOVJ·MOVL과 OLP의 P·LP·JP 표시를 구현했다. 프로그램 패널의 `티칭 위치 표시`에서 텍스트 표시, ID만·라벨명만·둘 다 선택, 가려진 점 표시, 화면 맞춤을 사용할 수 있다. 선택한 점에는 자세축을 표시하며, 기존 프로그램 목록과 마커 선택을 연동한다. 별도의 큰 포인트 정보 영역과 선택 목록은 제거했다. 겹친 점은 반복 클릭하여 각각 선택한다. 수정·삭제 후 갱신, 표시 방식 저장·복구, 6개 언어 표시를 지원한다.

현재는 선택한 로봇을 표시한다. 3단계의 여러 로봇 동시 표시, 검색, 티칭 순서 연결선은 후속 범위로 유지한다. 텍스트는 처음 100개와 선택한 점으로 제한하며, 위치 마커에는 모든 유효 포인트를 포함한다. OLP의 기본 이름 P0·LP0·JP0는 ID와 중복 표시하지 않는다. 라벨명만 모드에서 라벨이 없는 점은 마커만 표시한다. 선택 전후의 글자는 실제 텍스트 비율을 유지한다.

초기 구현을 같은 PC의 Chromium headless 환경에서 SCARA 포인트 1,000개로 30회씩 측정했을 때, 렌더링과 GPU 완료를 포함한 처리 중앙값은 표시 해제 약 0.9 ms, 표시 활성화 약 2.0 ms였다. 절대 처리 시간은 짧지만 증가율 20%라는 초기 성능 목표에는 도달하지 못했다. 표시를 5회 반복 전환한 뒤 그래픽 자원 수가 누적되지 않는 것을 확인했다.

표시 UI 개선 후 빠른 검사 187개와 티칭 표시 브라우저 검사 7개가 통과했다. 전체 검증의 JavaScript 구문 검사 235개 파일, C# 브리지 빌드, 생성기 기준 출력 127개 비교도 통과했다. 브라우저 전체 179개 중 173개가 통과했고, 페이지 로딩 시간 초과 5개와 S25 충돌 검사의 재질 색상 조회 오류 1개가 발생했다. 로딩 시간 초과 5개는 재검사에서 통과했다. S25 충돌 검사는 복수 재질을 단일 재질처럼 읽는 `getHex` 오류가 재현되어 해당 충돌 표시 검증은 미완료이며, 전체 검증 실행은 실패로 기록한다. 요청한 티칭 표시 변경의 7개 검사는 전체 실행에서도 모두 통과했다.
