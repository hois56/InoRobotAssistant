# 시뮬레이션 충돌 검사 메모리 절감 계획서

- 대상: InoRobot Assistant `2_3DSimulation`
- 작성일: 2026-11-02
- 상태: 개발 계획
- 목표: 충돌 감지 기능과 판정 정확도를 유지하면서, 충돌 검색 구조를 만든 뒤에도 남아 있는 생성용 배열의 메모리를 줄인다.

## 1 적용 범위와 기대 효과

충돌 검색 구조인 BVH는 삼각형들을 경계 상자로 묶어, 실제 접촉 가능성이 있는 부분을 빠르게 찾는 구조다. 현재 구현은 이 구조를 만드는 데 사용하는 삼각형별 경계와 중심 좌표 배열을 구조 생성 후에도 보관한다. 이 두 배열을 생성 중에만 사용하는 지역 데이터로 바꾸고, 완성된 BVH와 원본 삼각형은 계속 유지한다.

사용자는 기존과 동일하게 충돌 감지와 충돌 시 정지를 사용할 수 있어야 한다. 모델의 형상, 색상, 표면 표현과 가져오기 품질도 유지한다.

메모리 절감은 **실제로 생성되어 보관 중인 BVH**에 적용된다. 충돌 기능이 꺼져 있고 경로 검사 등에서도 BVH를 만들지 않았다면 이번 변경으로 줄어드는 메모리는 없다. 따라서 STEP을 불러온 뒤 유지되는 약 5GB 전체를 이번 변경으로 해결한다고 전제하지 않는다.

STEP 변환기의 수명 관리, 반복 부품의 형상 공유, 경량 가져오기, 충돌 형상의 단순화는 이번 범위에서 제외한다.

## 2 현재 코드와 메모리 수명

수정 대상은 `collision-system.mjs`의 `GeometryBVH` 생성자와 비공개 `#build()`다.

| 데이터 | 현재 역할 | 변경 후 수명 |
|---|---|---|
| `localTriangleBounds` | 삼각형마다 최소와 최대 좌표 6개를 저장하고 BVH 노드의 범위를 계산 | 생성자와 재귀 빌드가 실행되는 동안만 유지 |
| `localTriangleCentroids` | 삼각형마다 중심 좌표 3개를 저장하고 BVH 분할 순서를 계산 | 생성자와 재귀 빌드가 실행되는 동안만 유지 |
| `root`와 하위 노드의 `bounds` | 충돌 검색 중 후보 범위를 판단 | 기존과 동일하게 유지 |
| 리프 노드의 `triangles` | 실제 검사할 삼각형 번호를 보관 | 기존과 동일하게 유지 |
| `geometry` | 실제 삼각형 좌표를 읽는 원본 | 기존과 동일하게 유지 |
| 충돌 결과와 좌표 변환 캐시 | 반복 검사와 이동한 모델의 결과 갱신 | 기존과 동일하게 유지 |

현재 두 생성용 배열의 참조는 생성자와 `#build()` 안에만 있다. 빌드가 끝난 뒤의 충돌 검색은 완성된 노드와 원본 형상을 사용한다. `readTriangleWorld()`는 원본 형상과 모델의 현재 변환 행렬로 좌표를 계산하며, 두 배열을 참조하지 않는다.

`MeshCollisionSystem.getGeometryBVH()`는 생성한 BVH를 `geometryCache`에 보관한다. 현재는 이 캐시가 살아 있는 동안 두 배열도 함께 유지되므로, 생성 직후 사용이 끝난 데이터가 장시간 남을 수 있다.

## 3 구현 방법

### 생성용 배열을 지역 데이터로 변경

1. 생성자의 `this.localTriangleBounds`, `this.localTriangleCentroids` 할당을 지역 배열로 변경한다.
2. 두 배열을 담은 빌드용 객체를 `#build(triangleIndices, buildData)`에 전달한다.
3. 재귀 호출에도 같은 객체를 전달하고, 기존의 노드 범위 계산과 분할 순서를 그대로 사용한다.
4. 완성된 노드에는 `bounds`, `left`, `right`, `triangles`만 기존과 동일하게 저장한다. 빌드용 객체나 이를 참조하는 함수를 BVH와 캐시에 저장하지 않는다.
5. 생성자가 반환된 뒤 두 배열이 다른 객체에 보관되지 않도록 한다. 생성 중 예외가 발생한 경우에도 빌드용 데이터를 캐시에 남기지 않는다.

지역 데이터의 수명으로 관리하면 정상 완료 후 해제 코드를 따로 호출할 필요가 없다. 배열이 도달 불가능해진 뒤 실제 메모리를 회수하는 시점은 JavaScript 런타임이 결정한다. 제품 코드에 강제 가비지 컬렉션 호출이나 주기적인 캐시 전체 초기화를 추가하지 않는다.

### 판정과 화면 동작 유지

배열의 자료형은 기존 `Float64Array`를 유지한다. 좌표 정밀도, 분할 축 선택, 정렬, 리프 크기, 허용 오차와 삼각형 교차 계산을 변경하지 않는다.

`getGeometryBVH()`, `prepare()`, `check()`, `checkAll()`, `isPointInside()`의 호출 방식과 결과 형식을 유지한다. 모델 이동과 회전, 캐시 재사용, 충돌 형상 교체, 캐시 정리도 기존 경로를 사용한다.

실제 충돌에 사용하는 원본 형상과 완성된 BVH는 계속 필요하므로 `geometry.dispose()`를 호출하거나 `geometryCache`를 비우는 방식으로 처리하지 않는다. 화면 렌더링과 충돌 판정 정책도 이번 변경에 포함하지 않는다.

## 4 예상 절감량과 한계

충돌 삼각형 수를 `T`라고 하면 두 배열의 데이터 크기는 다음과 같다.

```text
삼각형 경계: T × 6 × 8바이트
삼각형 중심: T × 3 × 8바이트
합계:        T × 72바이트
```

| 생성되어 유지 중인 BVH의 삼각형 합계 | 회수 대상 배열 크기 |
|---:|---:|
| 10만 개 | 7.2MB 약 6.9MiB |
| 100만 개 | 72MB 약 68.7MiB |
| 500만 개 | 360MB 약 343.3MiB |
| 1천만 개 | 720MB 약 686.6MiB |

계산에는 화면에 표시되는 삼각형 수가 아니라 **각 BVH가 실제 검사하는 형상의 삼각형 수**를 사용한다. 같은 캐시에서 하나의 형상을 공유하면 한 번만 계산한다. 충돌용 대체 형상을 사용하면 그 형상의 삼각형 수를 기준으로 한다.

이 값은 두 배열의 데이터 크기이며, 작업 관리자의 프로세스 사용량이 같은 양만큼 즉시 내려간다는 의미는 아니다. JavaScript와 브라우저의 메모리 재사용 정책이 측정값에 영향을 줄 수 있다.

단일 BVH를 만드는 동안에는 여전히 두 배열이 필요하므로 해당 빌드의 임시 할당량은 유지된다. STEP 변환 중 최대 메모리, 원본 형상, GPU 버퍼, 완성된 BVH 노드와 다른 캐시의 사용량은 이번 변경의 절감 대상이 아니다.

## 5 구현과 검증 순서

### 변경 전 재현과 기준 확보

충돌 관련 기존 미커밋 변경을 확인한 뒤, 동일한 모델과 자세에서 BVH를 준비하고 접촉 상태를 기록한다. 이어서 생성이 끝난 BVH에서 두 배열이 계속 도달 가능한지 확인하고, 배열의 실제 `byteLength` 합계를 구한다.

회귀 검사는 `tests/fast/simulation-collision-memory.test.mjs`에 추가하는 것을 기본으로 한다. 기존 충돌 성능 검사의 모듈 로딩 방식을 활용하고, 제품 코드에 검사 전용 내보내기나 화면 항목을 추가하지 않는다. 수정 전에는 생성용 배열이 계속 유지되는 조건에서 새 메모리 회귀 검사가 실패하는 것을 확인한다.

### 최소 변경 구현

`GeometryBVH` 내부의 데이터 수명과 재귀 호출 인자만 수정한다. `main.js`와 기존 충돌 정책은 유지한다. 기존 검사에서 추가 문제가 드러나면 관련 원인을 확인하고, 이번 변경과 무관한 개선을 섞지 않는다.

### 자동 검사

| 검사 항목 | 확인할 결과 |
|---|---|
| 생성 후 메모리 참조 | BVH가 원본 형상과 완성된 노드를 유지하면서 생성용 대형 배열을 더 이상 보관하지 않음 |
| 접촉과 분리 | 같은 입력에서 접촉 메시 쌍과 충돌 유무가 변경 전과 일치 |
| 반복 검사와 이동 | 같은 BVH 재사용, 이동과 회전 후 접촉 재검사, 분리 후 해제와 재접촉이 정상 |
| 포함 여부 | 닫힌 형상 내부와 외부, 표면 위 점, 열린 형상의 판정이 기존과 일치 |
| 준비와 수명 관리 | `prepare()` 반복 호출에서 불필요한 재생성 없음, 형상 교체와 캐시 정리 후에도 정상 |
| 경계 입력 | 빈 형상과 작은 형상에서 기존 반환 규칙 유지 |

메모리 검사는 소스의 필드명 유무만 확인하지 않고, 생성된 BVH가 실제로 보관하는 데이터와 충돌 동작을 함께 확인한다. Node의 관련 `ArrayBuffer` 사용량과 브라우저 힙 비교는 보조 측정으로 사용하고, 비동기 메모리 회수 시점에 의존하는 불안정한 통과 조건을 만들지 않는다.

기존 `tools/validate-collision-system.mjs`는 별도로 실행하여 삼각형 교차, 포함 판정, Tool 장착부 예외, BVH 준비와 재사용, 충돌 시 정지 흐름을 확인한다. 작업 중 빠른 검사가 필요하면 실제 수정 경로를 지정하여 실행한다.

```powershell
npm run test:changed -- 2_3DSimulation/collision-system.mjs tests/fast/simulation-collision-memory.test.mjs
```

완료 검사는 관련 빠른 검사와 브라우저 검사를 포함하는 다음 명령으로 실행한다. 완료 검사 직전에 같은 빠른 검사를 별도로 반복하지 않는다.

```powershell
npm run verify:changed -- 2_3DSimulation/collision-system.mjs tests/fast/simulation-collision-memory.test.mjs
node tools/validate-collision-system.mjs
```

브라우저 결과에서는 기존 `simulation-collision-performance`, `simulation-robot-collision`, `simulation-collision-scope` 검사와 자동 경로 관련 검사의 포함 여부 및 결과를 확인한다. 자동 선택에 필요한 동작 검사가 빠져 있으면 해당 검사를 추가 실행한다. 전체 저장소 검증은 이번 변경의 기본 완료 조건으로 두지 않는다.

### 실제 STEP과 화면 비교

같은 브라우저, 모델, 가져오기 품질과 카메라를 사용하여 변경 전후를 비교한다.

1. STEP을 불러온 뒤 동일한 로봇과 Tool을 배치하고, 충돌 검색 구조가 생성되도록 충돌 검사를 실행한다.
2. 준비 완료 후 BVH의 삼각형 합계와 생성용 배열의 유지 여부를 확인한다. 동일한 대기 조건과 개발 도구의 메모리 정리 조건에서 힙과 프로세스 사용량을 구분해 기록한다.
3. 충돌하지 않는 자세, 접촉 자세, 분리 후 재접촉을 차례로 재현한다. 기존 충돌 표시와 정지 동작이 유지되는지 확인한다.
4. 자동 경로의 충돌 판정과 형상 내부 판정도 기존 결과와 비교한다.
5. 모델 전체 화면과 접촉 부위의 확대 화면에서 형상, 색상, 외곽선이 기존과 같은지 비교한다.

약 5GB가 유지되는 실제 STEP을 사용할 수 있으면 같은 조건으로 추가 비교한다. 사용하지 못한 경우에는 합성 모델과 확보한 STEP의 결과를 구분하고, 실제 5GB 사례의 감소량을 추정값으로 확정하지 않는다.

## 6 완료 기준과 버전 기록

- BVH 생성 완료 후 두 대형 배열을 계속 보관하는 참조가 없다.
- 원본 형상과 완성된 BVH는 유지되고 충돌 검사와 캐시 재사용이 정상 동작한다.
- 관련 자동 검사와 화면 비교에서 충돌 유무, 포함 판정, 표시와 정지 동작의 차이가 없다.
- 절감량은 실제 생성된 BVH의 삼각형 수와 회수 대상 배열 크기로 설명하며, 모델 전체 사용량의 감소와 구분한다.
- `git diff --name-only`와 `git diff`로 이번 변경이 관련 코드, 검사와 버전 기록에 한정되는지 확인한다.

구현을 완료하면 같은 배포의 기존 버전 기록에 최종 사용자에게 보이는 개선만 묶어 기록하고, `node tools/build-version-history.cjs`로 생성 결과를 갱신한다. 기록 문구는 다음을 기준으로 한다.

> 복잡한 3D 모델의 충돌 검사에서 불필요한 메모리가 유지되던 문제를 해결했습니다.

계획서 작성 단계에서는 기능 버전 기록을 갱신하지 않는다.
