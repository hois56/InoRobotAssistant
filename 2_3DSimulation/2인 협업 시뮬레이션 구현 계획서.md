# 2인 협업 시뮬레이션 구현 계획서

- 작성일: 2026-09-02
- 대상: `2_3DSimulation`
- 목표: 두 대의 컴퓨터가 하나의 시뮬레이션 방에 접속하고, 각 PC에 연결된 컨트롤러로 서로 다른 로봇을 동시에 제어할 수 있도록 한다.

## 1. 개발 목표

현재는 한 PC의 웹페이지가 하나의 로컬 컨트롤러 연결만 사용할 수 있으므로, 로봇 2대를 동시에 컨트롤러로 시뮬레이션하기 어렵다. 이 기능에서는 각 PC가 자기 컨트롤러에 로컬로 연결된 상태를 유지하면서, 두 브라우저의 시뮬레이션 상태만 협업 서버를 통해 동기화한다.

### 핵심 완료 조건

1. 한 사용자가 방을 만들고 숫자 4자리 방 코드를 발급받을 수 있다.
2. 두 번째 사용자가 방 코드만 입력해 같은 시뮬레이션 방에 참여할 수 있다.
3. 두 사용자가 방 안에서 서로 다른 로봇을 하나씩 점유할 수 있다.
4. PC A의 컨트롤러로 로봇 1을 움직이면 PC B 화면의 로봇 1도 같은 자세로 갱신된다.
5. PC B의 컨트롤러로 로봇 2를 움직이면 PC A 화면의 로봇 2도 같은 자세로 갱신된다.
6. 한 사용자가 점유하지 않은 로봇에는 컨트롤러 동작을 적용할 수 없다.
7. 컨트롤러 연결 해제, 방 퇴장, 네트워크 재접속 시 로봇 상태와 제어권이 안전하게 처리된다.
8. 기존 단독 사용 모드와 로컬 컨트롤러 연결은 협업 기능을 사용하지 않아도 그대로 동작한다.

## 2. 범위와 기본 정책

### 2.1 1차 구현 범위

- 최대 2명의 사용자로 제한한다.
- 한 방에서 로봇별 제어권을 한 명에게만 부여한다.
- 방 생성자는 호스트가 되고, 참여자는 게스트가 된다.
- 각 브라우저는 자기 PC의 로컬 컨트롤러 브리지에 연결한다.
- 컨트롤러 원시 통신을 다른 PC로 전달하지 않고, 시뮬레이션에 필요한 관절 자세·상태·알람·연결 상태를 전달한다.
- 방 생성 시점의 시뮬레이션 작업 상태를 기준 스냅샷으로 공유한다.
- 방이 만들어진 후 발생한 로봇 자세와 협업 대상 장면 변경을 실시간 동기화한다.
- 네트워크가 끊겼다가 다시 연결되면 서버의 최신 스냅샷을 받아 복구한다.

### 2.2 1차 구현에서 제외하는 범위

- 한 로봇을 두 사용자가 동시에 조작하는 기능
- 3명 이상 접속 및 3대 이상의 컨트롤러
- 실제 컨트롤러를 원격 PC에서 직접 조작하기 위한 통신 터널링
- 서버에서 Three.js 장면을 렌더링하거나 물리 시뮬레이션을 실행하는 기능
- 협업 채팅, 음성 통화, 사용자별 상세 권한 관리
- 방이 종료된 후에도 서버에 작업을 영구 보관하는 기능

원격 사용자의 화면에 로봇 움직임을 보여주는 것은 포함하지만, 실제 컨트롤러 연결은 반드시 해당 컨트롤러가 연결된 PC에서 실행한다.

## 3. 현재 프로젝트 기준점

현재 3D 시뮬레이션은 브라우저에서 Three.js 모델을 렌더링하며, 컨트롤러 연결은 로컬 주소를 사용한다.

| 영역 | 현재 구현 | 협업 확장 방향 |
| --- | --- | --- |
| 시뮬레이션 화면 | `2_3DSimulation/index.html`, `main.js` | 협업 패널과 방 상태 표시 추가 |
| 컨트롤러 상태 | `state.virtualController` | 로컬 연결 상태는 유지하고 협업 상태를 별도 관리 |
| 대상 로봇 | `state.virtualController.targetRobotId` | 방의 `robotId`와 현재 컨트롤러 소유자를 매핑 |
| 컨트롤러 메시지 | `handleVirtualControllerMessage()` | 로컬 샘플을 시뮬레이션에 적용한 뒤 협업 서버로 전송 |
| 관절 변경 | `setJointAngle()` | 원격 상태 적용 시 재전송하지 않도록 원격 적용 컨텍스트 추가 |
| 작업 스냅샷 | `captureSceneSnapshot()`, `applySceneSnapshot()` | 방 입장·재접속용 공유 스냅샷으로 재사용 |
| 로컬 브리지 | `ws://127.0.0.1:5055/ws` | 원격 협업 WebSocket과 분리하여 유지 |
| 로컬 Virtual Bus | `ws://127.0.0.1:8765/virtualbus/` | 협업 데이터와 섞지 않고 기존 로컬 통신 전용으로 유지 |
| 로컬 서버 | `tools/serve-local.cjs` | 개발 환경에서 정적 파일과 협업 서버를 함께 실행할 수 있도록 선택적으로 확장 |

현재 로컬 컨트롤러 주소는 `127.0.0.1`이므로 다른 PC가 이 주소로 접속하도록 변경하면 안 된다. PC별 로컬 브리지는 각 PC에서 실행하고, 브라우저 간 공유만 별도 협업 WebSocket으로 처리한다.

## 4. 전체 아키텍처

```text
┌──────────────────────────┐       ┌──────────────────────────┐
│ PC A                     │       │ PC B                     │
│                          │       │                          │
│ 브라우저 A               │       │ 브라우저 B               │
│  ├─ 로봇 1 렌더링/제어   │       │  ├─ 로봇 2 렌더링/제어   │
│  ├─ 로컬 브리지 연결     │       │  ├─ 로컬 브리지 연결     │
│  └─ 협업 WebSocket       │       │  └─ 협업 WebSocket       │
└───────────┬──────────────┘       └───────────┬──────────────┘
            │                                  │
            └────────── 협업 서버 ─────────────┘
                 방 상태·로봇 상태·권한
```

### 4.1 서버 권한 모델

협업 서버는 방에 연결된 클라이언트와 로봇별 제어권을 관리한다. 클라이언트가 보낸 모든 메시지를 그대로 중계하지 않고 다음을 확인한다.

- 유효한 방 코드인지
- 방에 등록된 사용자 토큰인지
- 메시지의 `robotId`를 해당 사용자가 점유하고 있는지
- 메시지의 순번이 이전 상태보다 최신인지
- 메시지 크기와 전송 빈도가 제한을 넘지 않는지

로봇의 소유자만 해당 로봇의 관절 상태를 갱신할 수 있다. 서버는 유효한 상태만 같은 방의 모든 클라이언트에 전달한다.

### 4.2 권장 동기화 방식

Three.js 프레임 전체나 3D 모델 객체를 전송하지 않는다. 다음 두 종류를 구분한다.

| 데이터 | 동기화 방법 |
| --- | --- |
| 관절 위치·컨트롤러 상태 | 일정 주기의 최신 상태 스냅샷 |
| JOG 시작·정지·알람·연결 변경 | 이벤트 메시지 |
| 모델 추가·삭제·변환 | 명령 이벤트 후 서버가 확정 상태 브로드캐스트 |
| 작업 초기 상태·재접속 | 전체 방 스냅샷 |
| 카메라·패널·선택 UI | 로컬 전용 |

관절 상태는 현재 컨트롤러 샘플 수신 주기를 그대로 네트워크에 복제하지 않고, 협업용 전송 주기를 별도로 둔다. 1차 기본값은 20~30Hz로 하고, 서버는 로봇별 최신 상태만 전송해 오래된 패킷이 쌓이지 않도록 한다.

## 5. 방 코드 설계

### 5.1 방 생성

호스트가 협업 패널에서 `방 만들기`를 누르면 서버가 다음을 생성한다.

- `roomCode`: 숫자로 구성된 4자리 코드
- `roomToken`: 실제 WebSocket 인증에 사용하는 무작위 토큰
- `hostUserId`: 호스트 식별자
- `createdAt`, `lastActivityAt`: 만료 및 정리용 시간
- `workspaceSnapshot`: 방 생성 시점의 시뮬레이션 상태
- `robots`: 방에 포함된 로봇 목록과 점유 상태

방 코드는 `0/O`, `1/I`처럼 혼동하기 쉬운 문자를 제외한다. 화면에는 대문자와 문자 간 간격을 적용해 잘못 입력하는 문제를 줄인다.

방 코드만으로 실제 인증을 끝내지 않고, 접속 성공 후 서버가 발급한 사용자 토큰을 사용한다. 비활성 방은 일정 시간 후 만료시키고, 방 코드가 추측되어도 오래 사용할 수 없도록 한다.

### 5.2 방 참여

게스트는 협업 패널에서 방 코드를 입력한다.

```text
방 코드 입력
    ↓
서버 방 확인
    ↓
사용자 토큰 발급
    ↓
작업 스냅샷 수신
    ↓
로봇별 제어권 선택
    ↓
협업 연결 완료
```

방이 이미 2명으로 가득 찼거나 만료된 경우에는 참여하지 않고 원인을 표시한다. 게스트가 입장할 때 호스트의 로컬 화면 상태를 직접 복사하지 않고 서버가 보관한 기준 스냅샷을 사용한다.

## 6. 로봇별 제어권

### 6.1 배정 정책

방 입장 후 사용자는 제어할 로봇을 선택한다. 이미 다른 사용자가 점유한 로봇은 `다른 사용자가 제어 중`으로 표시하고 선택할 수 없다.

```text
로봇 1   PC A 제어 중
로봇 2   PC B 제어 가능
```

호스트는 참여자의 로봇 배정을 변경할 수 있다. 배정 변경 전에는 기존 소유자의 컨트롤러 동작을 정지시키고, 새 소유자가 확인한 뒤 제어권을 넘긴다.

### 6.2 제어권 안전 규칙

- 한 `robotId`에는 하나의 `ownerUserId`만 허용한다.
- 컨트롤러가 연결되지 않은 사용자는 해당 로봇에 동작 상태를 보낼 수 없다.
- 브라우저가 비정상 종료되면 서버 heartbeat 만료 후 제어권을 해제한다.
- 소유자가 방을 나가면 로봇을 정지 상태로 전환하고 로봇을 미배정 상태로 둔다.
- 제어권을 잃은 클라이언트의 늦게 도착한 상태 패킷은 서버에서 폐기한다.
- 상대 로봇의 화면 상태는 볼 수 있지만, JOG·프로그램 실행·리셋 명령은 실행할 수 없다.

## 7. 상태 및 메시지 설계

### 7.1 공통 메시지 형식

```json
{
  "type": "robotState",
  "roomToken": "...",
  "userId": "...",
  "robotId": "robot-instance-id",
  "sequence": 1842,
  "clientTime": 1788350000000,
  "payload": {}
}
```

모든 메시지는 `type`, 방 세션 식별자, 송신 사용자, 순번을 포함한다. 인증 토큰은 WebSocket handshake 또는 별도 인증 메시지에서 검증하고, 매 메시지에 노출할 필요가 없도록 한다.

### 7.2 1차 메시지 종류

| 메시지 | 방향 | 목적 |
| --- | --- | --- |
| `createRoom` | 클라이언트 → 서버 | 방 생성 요청 |
| `joinRoom` | 클라이언트 → 서버 | 방 코드로 참여 |
| `roomSnapshot` | 서버 → 클라이언트 | 방 상태와 초기 작업 전달 |
| `participantJoined` | 서버 → 클라이언트 | 사용자 입장 알림 |
| `participantLeft` | 서버 → 클라이언트 | 사용자 퇴장 알림 |
| `robotClaim` | 클라이언트 → 서버 | 로봇 제어권 요청 |
| `robotAssignment` | 서버 → 클라이언트 | 로봇 배정 결과 |
| `robotState` | 클라이언트 → 서버 | 소유 로봇의 관절·상태 전송 |
| `robotStateBroadcast` | 서버 → 클라이언트 | 검증된 로봇 상태 전달 |
| `robotCommand` | 클라이언트 → 서버 | 정지·리셋·JOG 상태 변경 요청 |
| `sceneCommand` | 클라이언트 → 서버 | 공유 장면 변경 요청 |
| `sceneCommandApplied` | 서버 → 클라이언트 | 확정된 장면 변경 전달 |
| `resyncRequest` | 클라이언트 → 서버 | 최신 스냅샷 요청 |
| `heartbeat` | 양방향 | 연결 확인 |
| `error` | 서버 → 클라이언트 | 요청 거부 및 오류 전달 |

### 7.3 로봇 상태 payload

```json
{
  "jointAngles": [0, 15.2, -30.5, 0, 90, 0],
  "tcpPose": {
    "position": [100, 200, 300],
    "rotation": [0, 0, 0, 1]
  },
  "connected": true,
  "streaming": true,
  "alarm": false,
  "estop": false,
  "controllerSource": "bridge"
}
```

관절값 배열의 길이와 각도 범위는 로봇 정의와 일치하는지 확인한다. 알 수 없는 로봇이나 잘못된 관절 개수의 상태는 적용하지 않는다.

## 8. 작업 스냅샷과 3D 모델 자산

### 8.1 공유 스냅샷

방 생성 시 다음 정보를 서버에 저장한다.

- 로봇 모델 종류와 `robotId`
- 각 로봇의 초기 관절값
- 장면 모델의 경로, 모델 종류, 위치, 회전, 표시 상태
- Tool, Arm Load, 간섭 영역, 작업 좌표 등 협업에 필요한 설정
- 현재 프로젝트 및 모션 프로그램의 식별 정보

기존 `serializeWorkspaceSnapshot()` 계열 저장 구조를 재사용하되, 브라우저 전용 객체·Three.js 객체·선택 UI는 제외한다.

### 8.2 대용량 모델 처리

3D 모델 파일을 관절 상태 메시지에 포함하지 않는다.

- 카탈로그 모델은 모델 ID와 고정된 웹 자산 경로만 공유한다.
- 사용자가 업로드한 STL, FBX, STEP 모델은 서버에 업로드하거나 두 사용자 모두 접근 가능한 저장 URL을 사용한다.
- 스냅샷에는 파일 전체가 아니라 `assetId`, `url`, `size`, `hash`를 저장한다.
- 참여자가 모델 자산을 갖고 있지 않으면 장면을 확정하지 않고 자산 다운로드 상태를 표시한다.
- 자산 업로드·다운로드는 협업 WebSocket과 분리된 HTTP 파일 전송으로 처리한다.

1차 개발은 카탈로그 모델을 우선 지원하고, 로컬 업로드 모델 공유는 자산 업로드 계층을 추가한 뒤 지원한다.

## 9. 클라이언트 구현 계획

### 9.1 협업 상태 추가

`main.js`의 기존 `state`에 다음과 같은 별도 상태를 추가한다.

```js
state.collaboration = {
    enabled: false,
    status: 'idle',
    role: null,
    roomCode: '',
    roomToken: null,
    userId: null,
    displayName: '',
    socket: null,
    participants: [],
    robotAssignments: new Map(),
    lastServerSequence: new Map(),
    applyingRemoteState: false,
    reconnectTimer: null
};
```

협업 상태와 기존 `state.virtualController`를 한 객체로 합치지 않는다. 로컬 컨트롤러 연결과 원격 협업 연결은 서로 다른 생명주기와 오류 처리를 가져야 한다.

### 9.2 로컬 샘플의 협업 전송

`handleVirtualControllerMessage()`에서 컨트롤러 상태를 받은 뒤 다음 순서로 처리한다.

```text
로컬 컨트롤러 샘플 수신
    ↓
기존 로컬 시뮬레이션 적용
    ↓
현재 사용자가 해당 로봇의 owner인지 확인
    ↓
협업 전송 주기에 맞춰 최신 상태 전송
    ↓
서버 검증 후 모든 클라이언트에 브로드캐스트
```

원격으로 받은 `robotStateBroadcast`는 `setJointAngle()`를 이용해 대상 로봇에 적용하되, `applyingRemoteState` 플래그를 사용해 다시 서버로 전송되는 순환을 막는다.

### 9.3 컨트롤러 연결 UI 변경

기존 컨트롤러 연결 패널에 다음 상태를 추가한다.

- `단독 사용` / `협업 사용` 모드
- 현재 방 코드
- 현재 사용자 이름 또는 PC 이름
- 내 제어 로봇
- 상대 사용자와 상대 제어 로봇
- 협업 서버 연결 상태
- 컨트롤러 로컬 연결 상태
- 방 나가기

협업 모드에서 컨트롤러 대상 로봇 선택 목록은 사용자가 점유한 로봇으로 제한한다. 아직 로봇을 배정받지 않았다면 컨트롤러 연결을 허용하지 않는다.

## 10. 서버 구현 계획

### 10.1 서버 구성

정적 웹페이지 서버와 협업 WebSocket 서버는 논리적으로 분리한다. 개발 환경에서는 하나의 Node 프로세스에서 실행할 수 있지만, 운영 환경에서는 정적 배포와 WebSocket 서버를 별도로 배포할 수 있어야 한다.

예상 구성은 다음과 같다.

```text
tools/collaboration-server.cjs
    ├─ HTTP health endpoint
    ├─ WebSocket /collaboration
    ├─ roomCode 생성 및 만료
    ├─ 사용자 인증 토큰 관리
    ├─ 로봇 점유권 검증
    ├─ 최신 상태 브로드캐스트
    └─ 재접속용 room snapshot 제공
```

기존 `tools/serve-local.cjs`의 로컬 Virtual Bus 역할과 협업 방 서버 역할은 분리한다. 두 연결을 같은 WebSocket 경로 또는 같은 인증 상태로 처리하지 않는다.

### 10.2 방 메모리 저장 정책

1차 버전은 서버 메모리 저장으로 시작한다.

- 서버 재시작 시 방과 연결은 종료된다.
- 비활성 방은 만료 후 메모리에서 제거한다.
- 각 방에는 최대 2명의 사용자만 허용한다.
- 최신 로봇 상태와 마지막 장면 스냅샷만 보관한다.
- 모든 상태 변경 이력을 영구 저장하지 않는다.

나중에 방 보존, 작업 공유, 초대 링크가 필요해지면 Redis 또는 DB를 추가한다.

## 11. 재접속과 장애 처리

### 11.1 브라우저 재접속

WebSocket이 끊어지면 클라이언트는 기존 방 코드와 사용자 토큰을 사용해 제한된 횟수로 재접속한다. 재접속 성공 후에는 누락된 이벤트를 순서대로 재생하지 않고, 서버의 최신 전체 스냅샷을 받아 장면과 로봇 상태를 맞춘다.

### 11.2 컨트롤러 연결 끊김

컨트롤러의 로컬 브리지가 끊기면 다음을 실행한다.

1. 해당 로봇의 로컬 모션을 정지한다.
2. 서버에 `connected: false`, `streaming: false` 상태를 전송한다.
3. 다른 화면에 해당 로봇을 정지·연결 끊김 상태로 표시한다.
4. 자동 재연결이 성공하면 새 상태 스냅샷을 먼저 전송한다.

### 11.3 오래된 패킷

로봇별 `sequence`와 `serverSequence`를 관리한다. 이미 적용한 순번보다 오래된 상태는 무시하고, 서버 시간을 기준으로 비정상적으로 미래인 패킷도 적용하지 않는다.

## 12. 공유 장면 변경 정책

로봇 관절 상태와 장면 편집은 충돌 가능성이 다르므로 분리한다.

### 12.1 1차 동기화 대상

- 로봇 관절 위치
- 로봇 정지·리셋 상태
- 컨트롤러 연결 상태
- 공유 모델의 위치·회전·표시 상태
- 방의 초기 작업 스냅샷

### 12.2 장면 변경 충돌 정책

- 모델 이동·회전·삭제는 서버가 요청 순서대로 처리한다.
- 같은 모델을 편집하는 동안에는 해당 모델을 잠근다.
- 잠금 사용자가 연결을 잃으면 heartbeat 만료 후 잠금을 해제한다.
- 로봇별 제어권과 모델별 편집 잠금은 별도로 관리한다.
- Undo/Redo는 1차 구현에서 호스트만 실행할 수 있도록 제한하거나, 장면 명령의 역연산을 서버에 추가하기 전까지 로컬 전용으로 둔다.

1차 기능의 핵심은 서로 다른 로봇을 동시에 조작하는 것이므로, 모델 편집 동기화는 로봇 상태 동기화 이후 단계에서 추가한다.

## 15. 검증 계획

### 15.1 자동 검증

`tools/validate-collaboration.mjs`에서 다음을 검사한다.

- 방 코드가 허용 문자와 길이를 만족하는지
- 중복 방 코드가 생성되지 않는지
- 최대 인원이 2명으로 제한되는지
- 알 수 없는 방·사용자·로봇의 요청이 거부되는지
- 다른 사용자가 점유한 로봇의 상태 변경이 거부되는지
- 오래된 `sequence`가 무시되는지
- 잘못된 관절 개수·범위·자료형이 거부되는지
- 로봇 상태 스냅샷이 JSON 직렬화 가능한지
- 재접속 시 최신 상태가 복구되는지
- 메시지 크기와 빈도 제한이 동작하는지

### 15.2 브라우저 수동 검증

1. PC A에서 방을 생성하고 방 코드가 표시되는지 확인한다.
2. PC B에서 방 코드로 참여하고 두 사용자 이름이 양쪽에 표시되는지 확인한다.
3. PC A에 로봇 1, PC B에 로봇 2를 배정한다.
4. 각 PC에서 자기 로봇의 컨트롤러를 연결한다.
5. PC A에서 로봇 1을 JOG하고 PC B 화면의 로봇 1이 같은 자세로 움직이는지 확인한다.
6. PC B에서 로봇 2를 JOG하고 PC A 화면의 로봇 2가 같은 자세로 움직이는지 확인한다.
7. 상대 로봇을 컨트롤러 대상으로 선택하거나 조작할 수 없는지 확인한다.
8. 한쪽 컨트롤러를 끊었을 때 양쪽 화면에 정지·연결 해제 상태가 표시되는지 확인한다.
9. 한쪽 브라우저의 네트워크를 잠시 끊었다가 복구하고 최신 로봇 상태로 재동기화되는지 확인한다.
10. 호스트가 방을 나가거나 브라우저를 닫았을 때 제어권과 로봇이 안전하게 처리되는지 확인한다.
11. 3D 모델이 동일한 자산으로 로드되고, 대용량 모델이 WebSocket을 막지 않는지 확인한다.
12. 협업 모드를 종료한 뒤 기존 단독 컨트롤러 연결과 시뮬레이션이 정상 동작하는지 확인한다.

### 15.3 성능 기준

- 로봇 상태의 일반적인 화면 반영 지연은 같은 네트워크에서 150ms 이하를 목표로 한다.
- 오래된 관절 상태가 누적되어 화면이 과거 자세로 되돌아가지 않아야 한다.
- 한 사용자의 고주기 컨트롤러 샘플이 다른 사용자의 화면을 정지시키지 않아야 한다.
- 큰 모델 업로드·복구 중에도 heartbeat와 로봇 상태 채널이 유지되어야 한다.

## 17. 완료 전 요구사항 대조

- [ ] 방 코드만으로 두 번째 PC가 참여할 수 있다.
- [ ] 방은 최대 두 명을 허용한다.
- [ ] 두 사용자가 서로 다른 로봇을 각각 점유한다.
- [ ] 각 PC의 로컬 컨트롤러 연결이 유지된다.
- [ ] 로봇 1과 로봇 2의 관절 상태가 양쪽 브라우저에 동기화된다.
- [ ] 소유하지 않은 로봇에는 조작 명령을 적용할 수 없다.
- [ ] 컨트롤러 끊김과 네트워크 재접속 시 안전 상태로 처리된다.
- [ ] 단독 사용 모드의 기존 기능이 회귀하지 않는다.
- [ ] 자동 검증과 두 대의 실제 컴퓨터를 사용한 브라우저 검증을 완료한다.
- [ ] 구현 완료 시 최종 사용자에게 보이는 변경 사항만 버전 기록에 반영한다.

`두 대의 컴퓨터가 방 코드로 같은 3D 시뮬레이션에 참여해 각자 다른 로봇에 연결된 컨트롤러를 동시에 사용할 수 있도록 했습니다.`

이 계획의 구현 완료 기준은 단순히 두 브라우저가 같은 화면을 보는 것이 아니라, `방 생성 → 방 코드 참여 → 로봇별 제어권 배정 → 각 PC의 로컬 컨트롤러 연결 → 서로 다른 로봇 동시 조작 → 상태 동기화 → 연결 해제·재접속 복구` 전체 흐름이 안정적으로 동작하는 것이다.
